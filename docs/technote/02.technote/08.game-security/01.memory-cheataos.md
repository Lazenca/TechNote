## **Structure of Memory Cheat Tools**

* **Memory cheat tools typically operate in the following phases:**

| Step | Phase | Description |
| --- | --- | --- |
| 1 | Process attach | Attach to the target process using `ptrace()` to access the process address space from user mode. |
| 2 | Check process memory regions | Inspect the target process's memory layout (`/proc/pid/maps`) for efficient memory scanning and filtering. |
| 3 | Memory access | Read and modify target memory addresses using `ptrace()` or `/proc/pid/mem`. |

## **Process Attach**

### **ptrace()**

* **The `ptrace()` system call allows a tracer process to attach to a tracee in user mode to inspect, read, and modify its memory and registers.**
  + `ptrace()` is fundamentally used by debuggers and tracing tools like `gdb`, `strace`, and `ltrace`.
  + It can be leveraged to inject shellcode or redirect execution flow by overwriting critical data structures like the Global Offset Table (GOT).

### ptrace Synopsis

* **The function prototype of `ptrace` is defined as follows:**

```c title="ptrace()"
#include <sys/ptrace.h>
long ptrace(enum __ptrace_request request, pid_t pid, void *addr, void *data);
```

### ptrace Requests

* **Key requests used in `ptrace` include:**

| Request | Description |
| --- | --- |
| PTRACE_ATTACH | * Attaches to the process specified in `pid`, making it a tracee. <br/>+ Sends a `SIGSTOP` to the tracee, though the tracee may not stop immediately upon return.<br/>+ The tracer uses `waitpid(2)` to wait for the tracee to stop. |
| PTRACE_TRACEME | * Indicates that this process is to be traced by its parent.<br/>+ Avoid using this request if the parent process is not intended to trace the child. |
| PTRACE_PEEKTEXT<br/>PTRACE_PEEKDATA<br/>PTRACE_PEEKUSER | * Reads a word at the specified memory/user address within the tracee process.<br/>+ Can be used to dump memory segments (code and data) into a local buffer.<br/>+ Note that under Linux, `PEEKTEXT` and `PEEKDATA` are functionally identical. |
| PTRACE_POKETEXT<br/>PTRACE_POKEDATA<br/>PTRACE_POKEUSER | * Writes a word of data into the tracee's memory or user area. |
| PTRACE_GETREGS | * Copies the tracee's general-purpose registers to inspect CPU state.<br/>+ Each thread maintains its own independent register context. |
| PTRACE_SETREGS | * Modifies the tracee's register values.<br/>+ For example, overwrites the instruction pointer (PC/EIP/RIP) to point to injected shellcode. |
| PTRACE_CONT | * Resumes the execution of a stopped tracee process. |
| PTRACE_DETACH | * Detaches from the tracee process, allowing it to continue execution freely. |
| PTRACE_SYSCALL | * Resumes the tracee, stopping it upon entry to or exit from the next system call.<br/>+ Used to inspect and alter system call arguments and return values (e.g., in `strace`). |
| PTRACE_SINGLESTEP | * Executes a single CPU instruction in the tracee and then stops.<br/>+ Used to step through instructions and inspect register/memory state after each step. |
| PTRACE_GETSIGINFO | * Retrieves information about the signal that caused the tracee to stop.<br/>+ Copies signal metadata into a `siginfo_t` structure. |
| PTRACE_SETSIGINFO | * Overwrites signal information in the tracee.<br/>+ Passes customized signal data using a `siginfo_t` structure. |
| PTRACE_SETOPTIONS | * Configures ptrace options on the tracee using a bitmask of flags.<br/>+ Refer to the `ptrace(2)` man page for available option flags. |

:::note[man page - ptrace (process trace)]
* <http://man7.org/linux/man-pages/man2/ptrace.2.html>
:::

## **Check the Process Memory Area**

### **/proc/pid/maps**

* **Understanding the `/proc/pid/maps` file layout is critical for memory scanning:**

```sh title="/proc/self/maps"

```

* **Fields in the maps file:**

| Field | Description |
| --- | --- |
| address | Virtual address range mapped to the process. |
| perms | Access permissions for the region:<br/>+ `r`: read<br/>+ `w`: write<br/>+ `x`: execute<br/>+ `s`: shared<br/>+ `p`: private (copy on write) |
| offset | Offset within the backing file. |
| dev | Major and minor device numbers (`major:minor`). |
| inode | Inode number of the mapped file (0 indicates anonymous memory not associated with a file). |
| pathname | Path of the mapped file or special tag (e.g., `[heap]`, `[stack]`, `[anon:libc_malloc]`). |

* **In `Lazenca-A-Android`, memory regions are filtered using the following logic:**
  + Filtering rules should be adjusted depending on the specific game engine (e.g., Unity, Unreal, Cocos2d).

```c title="MapsListFiltering()"
void MapsListFiltering(){
	for(int i = 0;i < mapsList.size();i++){
		maps = mapsList.at(i);

		if(!strstr(maps.strPerms,"rw-p")){
			continue;
		}else if(strstr(maps.strPath,"/system/bin")){
			continue;
		}else if(strstr(maps.strPath,"/system/lib")){
			continue;
		}else if(strstr(maps.strPath,"/system/vendor")){
			continue;
		}else if(strstr(maps.strPath,"/dev/ashmem")){
			if(!strstr(maps.strPath,"/dev/ashmem/dalvik-heap")){
				continue;
			}
		}else if(strstr(maps.strPath,"")){
			continue;
		}
		memReadAreaList.push_back(maps);
	}
}
```

* **Filter criteria summary:**

| Field | Filtering Rule |
| --- | --- |
| **perms** | Scan only regions with writable private permissions (`rw-p`). |
| **pathname** | Exclude system binaries (`/system/bin`), system libraries (`/system/lib`), and vendor drivers (`/system/vendor`).<br/>Exclude `/dev/ashmem` regions unless they correspond to `/dev/ashmem/dalvik-heap`.<br/>Optionally filter out standard `[anon:libc_malloc]` regions or native anonymous memory as needed. |

## **Memory Read**

### **ptrace()**

* **Reading target process memory using `ptrace()`:**
  + Attach to the target process using `PTRACE_ATTACH`.
  + Read memory words using `PTRACE_PEEKDATA`.
  + Detach from the target using `PTRACE_DETACH`.

```c title="readData()"
void readData(int pid, void* address){
	ptrace(PTRACE_ATTACH, pid, NULL, NULL);
	long value = ptrace(PTRACE_PEEKDATA, pid, (void *) address, NULL);
	ptrace(PTRACE_DETACH, pid, NULL, NULL);
}
```

### **/proc/pid/mem**

* **Using `PTRACE_PEEKDATA` word-by-word over massive memory spaces introduces severe performance bottlenecks:**
  + Excessive context switching between processes
  + Very slow scan throughput
* **To overcome this, bulk memory reading is performed directly via `/proc/pid/mem`:**
  + Open `/proc/pid/mem` using `open()` to obtain a file descriptor.
  + Seek to the target start address with `lseek()`.
  + Read large blocks into a memory buffer with `read()`.

```c title="getValue()"
void getValue(int mem_fd, long staMemAddr, long endMemAddr, void *buf){
	void* address;
	void* value;

	printf("staMemAddr : %#lx, endMemAddr : %#lx\n", staMemAddr, endMemAddr);

	for (; staMemAddr < endMemAddr; staMemAddr += 4096) {
		printf("fd : %d, staMemAddr : %#lx, endMemAddr : %#lx\n", mem_fd, staMemAddr, endMemAddr);
		lseek(mem_fd, staMemAddr, SEEK_SET);
		read(mem_fd, buf, MEMREADSIZE);
		for (int j = 0; j < MEMREADSIZE / 4; j++) {
			address = (void*) (staMemAddr + (j * 4));
			value = ((long**) buf)[j];
			printf("address : %#lx, Value : %ld\n", (long)address, (long)value);
		}
	}
}
```

:::info[lseek() - Linux man page]
* Use `lseek()` to reposition the read/write file offset to the desired virtual memory address.
  + [http://man7.org/linux/man-pages/man2/lseek.2.html](http://man7.org/linux/man-pages/man2/lseek.2.html)
:::

## **Memory Write**

### **ptrace()**

* **Modifying memory values using `ptrace()`:**
  + Attach to the target process using `PTRACE_ATTACH`.
  + Write the new word to the target address using `PTRACE_POKEDATA`.
  + Detach using `PTRACE_DETACH`.

```c title="writeData()"
void writeData(int pid, void* address, void* value){
	ptrace(PTRACE_ATTACH, pid, NULL, NULL);
	ptrace(PTRACE_POKEDATA, pid, (void *) address, (void *) value);
	ptrace(PTRACE_DETACH, pid, NULL, NULL);
}
```

* **Modifying memory values via `/proc/pid/mem`:**

## **Memory Fuzzing (Differential Search)**

* **Cheat tools provide differential fuzzing / searching modes:**
  + Unchanged value (value equals previous scan)
  + Changed value (value does not equal previous scan)
  + Increased value (value is greater than previous scan)
  + Decreased value (value is less than previous scan)
* **Differential search workflow:**
  1. Initialize scan: Read and snapshot all candidate memory values into memory or a temporary cache file.
  2. Perform in-game action that alters the value (e.g., gain/spend gold or take damage).
  3. Compare: Scan the memory again and filter candidate addresses according to the chosen condition (e.g., increased/decreased).
  4. Repeat iteratively until only 1 or a few candidate memory addresses remain.

## **Memory Lock (Freeze Value)**

* **Memory locking freezes a value at a specific address:**
  + Spawn a dedicated background thread.
  + In a loop, continuously write the desired constant value to the target memory address via `ptrace()` or `/proc/pid/mem`.
