# **Game Security Guide - Memory cheat**

* **Many game development companies deploy commercial game security solutions to mitigate damages caused by cheating.**
  + Some assume that applying a commercial security solution will magically block all cheats.
  + However, most security solutions are designed to make cheating significantly harder rather than completely impossible.
  + **Security solutions achieve maximum efficacy only when paired with secure coding practices in the core game codebase.**
* **This page provides a guide on defensive techniques to prevent in-game cheating via memory modification tools.**

:::warning
* Cheating attempts may still occur even after implementing these security patterns; defense-in-depth is essential.
:::

## **Anti-Debugging**

### **ptrace()**

* **The following code checks if an external process (such as a debugger or memory cheat tool) has attached to the target process:**
  + This is a fundamental and common anti-debugging technique.
  + If the current process is not being traced, `ptrace(PTRACE_TRACEME, ...)` returns `0`; if it is already being traced, it returns non-zero (`-1`).
  + This check helps verify whether a debugger or cheat tool is currently attached to the game process.

```c title="ptrace()"
int result = ptrace(PTRACE_TRACEME, 0, 0, 0);

if(result != 0){
  exit(0);
}
```

## **Memory Cheat Tools**

* **Before implementing defensive code, it is important to understand how memory cheat tools search for and isolate target variables:**
* **Memory cheat tools narrow down values using multi-step scanning:**
  + 1st Scan: The cheat tool searches game memory for an initial numeric value.
    - All memory addresses matching the searched value are saved into a candidate list.
  + 2nd Scan: The cheat tool does not rescan the entire memory space.
    - It only re-evaluates the addresses in the saved candidate list, checking which ones match the new (updated) value.
    - Addresses matching the new value are retained, and non-matching addresses are discarded.
  + 3rd+ Scan: After several consecutive scans, the specific memory location controlling the game variable is isolated.

## **Secure Game Coding Practices**

* **The following patterns protect sensitive in-game variables (e.g., gold, health, score) from memory scanning and modification:**

### Value Splitting (Division)

* **Splitting a single logical value across multiple distinct variables protects it from direct memory searches:**
  + Because the value rendered on screen is split across multiple variables, the plain numerical value never appears in memory for cheat engines to scan.
  + Example:
    - On-screen display value: 100 (`value1 + value2`)
    - Stored memory values: `value1` (32), `value2` (68)

```c title="DivisionValue()"
static int value1= 0, value2 = 0, value3 = 0, total = 0;

int Util::DivisionValue(int value){
    value3 = value1;
    value1 = getRandomNumber(0, value1 + value2 + value);
 
    value2 = value3 + value2 + value - value1; 
    return value1 + value2;
}

int Util::getRandomNumber(int from, int to){
    return (int)from + arc4random() % (to-from+1);
}
```

### XOR Masking

* **Applying an XOR mask with dynamic salt prevents raw numerical values from being discovered:**
  + Because the variable in memory is masked via XOR, cheat tools searching for plain integers will fail to locate it.
  + Example:
    - Plain value: 100
    - Masked in memory: `100 ^ salt`

```c title="XOREncrypt"
int Util::XOREncrypt(int value){
    srand((unsigned int)time(NULL));
    salt = rand() % 10;
    encode = value ^ salt;

    return encode;
}
int Util::XORDecrypt(int encode){
    return encode ^ salt;
}
```

### Dynamic Memory Relocation (Reallocation)

* **Reallocating the memory location of sensitive values on every mutation breaks iterative scan narrowing:**
  + Because the storage address changes whenever the value updates, iterative narrowing scans in cheat tools (which assume static memory addresses) are invalidated.
  + Example:
    - 1st update: 100 at `0x601000`
    - 2nd update: 200 at `0x601480`
    - 3rd update: 300 at `0x601780`
    - ...

```c title="MemoryRealloc"
int *score = new int;
...
delete score;
```
