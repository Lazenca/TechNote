## **Debugging kernel and modules**

* **There are various ways to debug the Linux kernel. Here, we explain kernel debugging using VMware.**

## **Debug Symbol Packages**

* **Install Debug Symbols for analysis convenience.**

### **Getting -dbgsym.ddeb packages**

* Add the repository configuration to `/etc/apt/sources.list.d/ddebs.list` as follows:

```sh title="/etc/apt/sources.list.d/ddebs.list"
echo "deb http://ddebs.ubuntu.com $(lsb_release -cs) main restricted universe multiverse
deb http://ddebs.ubuntu.com $(lsb_release -cs)-updates main restricted universe multiverse
deb http://ddebs.ubuntu.com $(lsb_release -cs)-proposed main restricted universe multiverse" | \
sudo tee -a /etc/apt/sources.list.d/ddebs.list
```

* Import the debug symbol archive signing key from the Ubuntu server:

```sh title="Install ubuntu-dbgsym-keyring"
sudo apt install ubuntu-dbgsym-keyring
```

### Manual install of debug packages

* Install the debug packages matching your current kernel version:

```sh title="Install Debug Symbols"
sudo apt-get update
sudo apt-get install linux-image-$(uname -r)-dbgsym
```

* The installed debug symbols are located at the following path:

```sh title="Location of Debug Symbols"
/usr/lib/debug/boot/vmlinux-$(uname -r)
```

## **Debugging Kernel and Modules with VMware**

### **Debugging Preferences to VMware - debugStub**

* **To debug the kernel with VMware, open the target VM's `*.vmx` file and add the following settings:**
  + Add the appropriate configuration depending on your target system environment (32-bit or 64-bit).

```txt title="VMware DebugStub Options - x86"
debugStub.listen.guest32 = "TRUE"
debugStub.listen.guest32.remote = "TRUE"
debugStub.hideBreakpoints = "FALSE"
monitor.debugOnStartGuest32 = "TRUE"
```

```txt title="VMware DebugStub Options - x86-64"
debugStub.listen.guest64 = "TRUE"
debugStub.listen.guest64.remote = "TRUE"
debugStub.hideBreakpoints = "FALSE"
monitor.debugOnStartGuest64 = "TRUE"
```

### Kernel Address Display Restriction (KADR)

* **Before debugging, it is necessary to understand Kernel Address Display Restriction (KADR):**
  + When an attacker attempts to exploit a kernel vulnerability, information such as gadget addresses and kernel function addresses is required just like user space exploitation.
  + **In the kernel, KADR treats kernel space addresses as sensitive information and hides them from regular local users.**
  + **Only root users are allowed to read various kernel introspection files and directories:**
    - `/boot/vmlinuz*`, `/boot/System.map*`, `/sys/kernel/debug/`, `/proc/slabinfo`
  + Since Ubuntu 11.04, `/proc/sys/kernel/kptr_restrict` defaults to `1` to block leaking known kernel addresses.
    - Set this value to `0` to disable the restriction.
* **When a regular user reads `/proc/kallsyms` (which stores all kernel symbols), the addresses are masked as `0000000000000000`:**
  + Reading the file as root displays the actual address values for each symbol.

### perf_event_paranoid

* **The reason addresses remain masked even after `kptr_restrict=0` is `perf_event_paranoid`.**
* **`perf_event_paranoid` controls access permissions for performance monitoring counters in the kernel.**

:::note[Option]

| Value | Description |
| --- | --- |
| 2 | Allow only user-space measurements (default since Linux 4.6) |
| 1 | Allow both kernel and user-space measurements (default prior to Linux 4.6) |
| 0 | Allow access to CPU-specific data (excluding raw tracepoint samples) |
| -1 | No restrictions |

:::

* **Setting `perf_event_paranoid` to 1, 0, or -1 allows regular users to inspect kernel symbol addresses:**

```sh title="sudo sysctl kernel.perf_event_paranoid = 0"
lazenca0x0@ubuntu:~/Kernel/Module/escalation$ sudo sysctl kernel.perf_event_paranoid
kernel.perf_event_paranoid = 3
lazenca0x0@ubuntu:~/Kernel/Module/escalation$ sudo sysctl -w kernel.perf_event_paranoid=0
kernel.perf_event_paranoid = 0
lazenca0x0@ubuntu:~/Kernel/Module/escalation$ cat /proc/kallsyms |grep escalation
```

### Debugging Modules

* **Set a breakpoint at the entry point of `chardev_ioctl` to begin dynamic debugging:**

```sh title="Setting a breakpoint"
(gdb) b *0xffffffffc0301075
Breakpoint 1 at 0xffffffffc0301075
(gdb) c
Continuing.
```

* **Run the `Exploit` program on the guest machine:**

```sh title="Executing the Exploit program"
lazenca0x0@ubuntu:~/Kernel/Module/escalation$ ./Exploit
```

* **GDB hits the breakpoint, allowing interactive dynamic debugging:**
  + With debug symbols loaded, function names used by the module are resolved and printed.

### **Debugging Preferences to VMware - serial port**

* **In addition to VMware's debugStub, you can also use a virtual serial port for kernel debugging.**
* **Add the following settings to the respective `*.vmx` files:**

```txt title="Server(Debug)"
serial0.present = "TRUE"
serial0.fileType = "pipe"
serial0.fileName = "/private/tmp/com1"
serial0.tryNoRxLoss = "FALSE"
serial0.pipe.endPoint = "server"
```

```txt title="Client(GDB)"
serial0.present = "TRUE"
serial0.fileType = "pipe"
serial0.fileName = "/private/tmp/com1"
serial0.tryNoRxLoss = "FALSE"
serial0.pipe.endPoint = "client"
```

* **Add `kgdbwait kgdboc/ttyS0,115200` to `GRUB_CMDLINE_LINUX_DEFAULT` in `/etc/default/grub`:**

```sh title="GRUB setting"
# If you change this file, run 'update-grub' afterwards to update
# /boot/grub/grub.cfg.
# For full documentation of the options in this file, see:
#   info -f grub -n 'Simple configuration'

GRUB_DEFAULT=0
GRUB_TIMEOUT_STYLE=hidden
GRUB_TIMEOUT=0
GRUB_DISTRIBUTOR=`lsb_release -i -s 2> /dev/null || echo Debian`
GRUB_CMDLINE_LINUX_DEFAULT="quiet nokaslr"
GRUB_CMDLINE_LINUX="find_preseed=/preseed.cfg auto noprompt priority=critical locale=en_US"

# Uncomment to enable BadRAM filtering, modify to suit your needs
# This works with Linux (no patch required) and with any kernel that obtains
# the memory map information from GRUB (GNU Mach, kernel of FreeBSD ...)
#GRUB_BADRAM="0x01234567,0xfefefefe,0x89abcdef,0xefefefef"

# Uncomment to disable graphical terminal (grub-pc only)
#GRUB_TERMINAL=console

# The resolution used on graphical terminal
# note that you can use only modes which your graphic card supports via VBE
# you can see them in real GRUB with the command `vbeinfo'
#GRUB_GFXMODE=640x480
```

* Update GRUB configuration:

